# ADR-0009: M1 fence mechanism — per-CPU count, no BPF atomics (amends ADR-0008 §(f))

## Status

Accepted (M1 Task 02, 2026-10-03). Supplements ADR-0008 §(f): the
protocol guarantees (admission, refusal, drain-wait, receipt rules)
are unchanged; only the mechanism changes. ADR-0008 is not edited in
place.

## Context

ADR-0008 §(f) specified a single 64-bit fence word (bit 63 `CLOSED` +
63-bit count) with BPF-side `fetch_add` admission, pending Task 02
codegen proof. The proof failed at compile time: the BPF target
leaves `target_has_atomic` unset, so `core::sync::atomic` RMW methods
(`fetch_add`/`fetch_sub`/`fetch_or`) do not exist for BPF programs
(`E0599`, witnessed in `gate-build-bpf-ctx.log`). There is no BPF-side
fetch of any kind in this toolchain — no fetch-add, no XADD-with-
result, no compare-exchange intrinsic. The single-word design is
unimplementable without inline-asm ISA emission (fragile,
toolchain-sensitive, verifier-risky).

## Decision

Replace the single word with two controls (M1 control ABI v1, final):

- `KCTLCLOSED`: `Array<u8>`, 1 slot. `0` = open, nonzero = closed.
  Written by userspace open/close, read by BPF admission.
- `KCTLCOUNT`: `PerCpuArray<u64>`, 1 slot. Active-writer count per
  CPU lane. BPF owns its own lane with plain ops (the same idiom as
  every existing per-CPU counter in the sensor); userspace folds all
  lanes at drain-wait.

Admission is increment-then-check (never check-then-increment):

1. BPF hook entry: `count[this_cpu] += 1` (saturating), then read
   `CLOSED`. Closed (or unreadable control — fail-closed) →
   decrement and refuse WITHOUT touching any data map or the ring.
2. Admitted hooks run the whole body; the single wrapper epilogue
   decrements after the last write.
3. Userspace close: write `CLOSED = 1`, then poll all lanes to zero
   with a 5 s deadline (1 ms rounds). All-zero → record the
   completion bound and issue the `Quiescent` receipt.
4. Timeout (deadline exhausted with writers inside) yields `Pending`:
   no receipt, no exact accounting — the sample stays a non-atomic
   sample. Map faults fail loud (`MapOpsError`).
5. The close runs BEFORE link close in `finish_session`; the receipt
   rides `AggregateTerminalSample.fence`. Open writes `CLOSED = 0`
   explicitly before the first attach (fresh maps read zero; the
   step is explicit).

## Why increment-then-check is airtight

Check-then-increment races (the late increment lands after the
closer's final read). Increment-then-check does not, by real-time
ordering on cache-coherent memory:

- If a writer's increment lands before the closer's lane read, the
  closer sees `count >= 1` (an admitted writer has not released yet)
  and keeps waiting — unless the writer refused (no data written) or
  released (all its data written before the release, program order,
  hence visible to the closer's later map reads).
- If the increment lands after the closer's read (which saw zero),
  the writer's `CLOSED` read follows its own increment in program
  order, hence follows the closer's `CLOSED` write in real time, so
  it observes closed and refuses — writing nothing after the bound.

A writer emits data only when it observed `CLOSED` clear, which
places its increment before the close write, which places it before
every drain read — so every data-emitting writer is waited for. No
fetch, no cross-CPU RMW, no BPF atomics anywhere.

## Consequences

- The privileged lane proves live drain behavior (close refuses
  entrants, waits for admitted writers, timeout → `Pending`) instead
  of atomic codegen; the fence uses only map lookup/update and plain
  arithmetic, like every existing counter.
- Refused writers briefly bump their lane count (increment, observe
  closed, decrement): the closer may spin extra rounds, never
  wrongly conclude. Count saturation uses saturating ops (63-bit
  headroom is unreachable in practice).
- Userspace-only interleaving tests keep running against faithful
  twins (`kcrypto_fence::bpf_admit_twins`) over heap words with the
  same op sequence.
- ADR-0008 §§(a)–(e),(g)–(i) are untouched; §(f)'s six protocol
  items hold with "the count" read as "every `KCTLCOUNT` lane" and
  "the close RMW" read as "the `CLOSED` write".

  `load_kcrypto_configured`, close in `finish_session`.

# ADR-0010: M1 fence close order + visibility grace (amends ADR-0009)

## Status

Accepted (M1 Task 02, 2026-10-03). Supplements ADR-0009: the fence
mechanism (per-CPU count, increment-then-check, `CLOSED` refusal,
`Pending` rules) is unchanged; only the userspace close sequence
changes. ADR-0009 is not edited in place.

## Context

External review (codex gpt-6.1-sol max, Task02 review F1, triaged
TRUE POSITIVE) found the close-ordering proof gap in
`finish_session`: the close ran `CLOSED = 1`, polled lanes to zero
once, issued the `Quiescent` receipt, and only then closed the
links. ADR-0009's "airtight" argument conflated a BPF store
*landing* (program order on the writer's CPU) with it being
*visible* to the closer's map read (cross-CPU visibility latency):
a writer admitted before `CLOSED` whose increment was still
invisible at the single all-zero poll would miss the scan, keep
running, and write maps while the terminal reads ran — a torn
terminal read behind a `Quiescent` receipt. (Post-receipt gap
invocations cannot be admitted — `CLOSED` is set, they refuse
harmlessly — so the hole is purely the visibility race, not late
admission.)

## Decision

Close order is detach-first with a visibility grace + rescan, in one
structural path (`detach_and_close_fence`, the ONLY fence path —
`finish_session` never calls `close_kernel_fence` directly):

1. Detach links FIRST (`links.clear()`): no new BPF invocation can
   start past detach — fast quiescence under load (no refusal churn
   in the drain polls) and a crisp session bound (nothing executes
   past detach).
2. Write `CLOSED = 1`: laggards (invocations entered before detach
   completed) refuse without touching any data map or the ring (the
   admit gate is top-of-path in every hook wrapper).
3. Poll all `KCTLCOUNT` lanes to zero (5 s deadline, 1 ms rounds):
   drains admitted stragglers.
4. At all-zero, sleep a 5 ms visibility grace and re-scan: only a
   second all-zero read issues the `Quiescent` receipt (grace burns
   deadline like any other wait).

## Why this is airtight (no residual)

After the grace, any admitted increment is visible (>5 ms invisible
stores are impossible — visibility latency is ns–µs); no new
admission can start past detach + `CLOSED`. The second all-zero read
therefore proves every admitted writer released, and each writer's
decrement follows its last write in program order — so the terminal
reads observe frozen maps. `Pending`/map-fault rules are unchanged.

## Consequences

- The privileged hammer test
  (`finish_session_quiescent_under_hammer_freezes_terminal`) locks
  the behavior: 4 threads hammering AF_ALG roundtrips through a real
  `finish_session` still quiesce fast (< 4 s) with a
  contradiction-free (all-Some), frozen terminal. It is a
  characterization lock, not a bug-catcher: the old race window is
  microseconds per close (3/3 pass on the old order too) — the order
  is proven by construction above.
- Post-detach traffic is unobserved by BOTH ledgers (previously
  post-`CLOSED` traffic was refused by `KCTX` only in stops after
  detach — consistent either way; the session bound is now detach).
- ADR-0009 §§(mechanism, admission, refusal, twins) are untouched;
  its step 5 ("close runs BEFORE link close") is superseded by the
  detach-first order here, and "airtight" now rests on the
  grace+rescan argument above.

## Enforcement / provenance

- Userspace: `close_kernel_fence` grace + rescan in
  `crates/kryprobe-privilege/src/kcrypto_fence.rs`,
  `detach_and_close_fence` in
  `crates/kryprobe-privilege/src/kcrypto_backend/session.rs`.
- No BPF change (admit/release protocol untouched).

# ADR-0007: dual session drivers — batch vs live-loop split blessed

## Status

Accepted (krypto-driver-seam Task 1, 2026-10-01). Owner decision:
bless the split, not convergence. Docs-only record; no production
behavior change.

## Context

The audit's driver findings (#1/#11) observe that kryprobe drives
the frozen `Backend` lifecycle from two places: the batch
`BackendDriver::run` pass and the live tick-loop sessions
(`drive_session`, `drive_lifecycle_session`). Structural
convergence of the two drivers was deferred as P2 in
`tasks/done/krypto-audit-fixes.md` ("Deferred structural: ...
P2 (driver convergence)"), and the owner has since blessed the
split instead: the two drivers stay separate, and a conformance
suite (Task 2 of this plan) gates drift between them.

The split is load-bearing, not incidental. The batch driver routes
a fixed event slice through every registered backend in one pass;
the live drivers own sensors, tick cadence, drains, stop handling,
and measurement-assembled coverage that a batch pass cannot
reproduce. Converging them would couple the offline harness path
to privilege-land transport (rings, drains, signal handling) or
strip the live path of its session machinery. This ADR records
exactly what each driver owns, what they share, and the contract
the conformance suite enforces.

## Decision

1. The dual-driver shape is blessed. `BackendDriver::run`
   (`crates/kryprobe-core/src/backend/driver.rs:117`) owns batch
   routing: one lifecycle pass over owned session state, events
   routed by header `backend_id`, each backend driven
   detect → plan → configure → decode → finalize in
   registration order (`drive_one`,
   `crates/kryprobe-core/src/backend/driver.rs:145`). The live
   loops own live capture: `drive_session`
   (`crates/kryprobe-cli/src/live.rs:1475`, aggregate profile)
   and `drive_lifecycle_session`
   (`crates/kryprobe-cli/src/live.rs:1829`, request-lifecycle
   profile) own the tick loop, sensor reads, drains, stop/SIGINT
   handling, latest-per-key accumulation, stop-time
   reconciliation, and measurement-assembled coverage.
2. The seam is shared vocabulary + shared per-event decode, used
   through identical call shapes on both sides:
   - Backend resolution: both sides resolve backends through
     `BackendRegistry`
     (`crates/kryprobe-core/src/backend/registry.rs:18`,
     `discover_all` at `:52`), and registry + live entry points
     both select the kcrypto profile through
     `register_kcrypto_profile`
     (`crates/kryprobe-privilege/src/kcrypto_backend/mod.rs:397`),
     so the two sides can never choose different
     profiles/decoders (`run_live_capture`,
     `crates/kryprobe-cli/src/live.rs:2160`).
   - Per-event decode: both sides decode every event through the
     frozen `Backend::decode`
     (`crates/kryprobe-core/src/backend.rs:149`) with a caller
     `DecodeContext` — batch at
     `crates/kryprobe-core/src/backend/driver.rs:195-201`,
     aggregate-live via `decode_tick_row`
     (`crates/kryprobe-cli/src/live.rs:677`, called at
     `:1603`/`:1620`/`:1636` for agg/totals/ident rows),
     lifecycle-live via the `decode_records` closure
     (`crates/kryprobe-cli/src/live.rs:1916`) through
     `lifecycle_event`
     (`crates/kryprobe-privilege/src/kcrypto_lifecycle/backend.rs:592`)
     plus `decode_tick_row` at `:1932`.
   - End-of-session facts: both sides file `BackendSummary`
     (`crates/kryprobe-core/src/backend/context.rs:109`) from
     `Backend::finalize`
     (`crates/kryprobe-core/src/backend.rs:155`) — batch inline
     at `driver.rs:204-210`, live ONCE per session
     (`live.rs:1712` aggregate, `live.rs:2078` lifecycle; never
     per tick).
   - Report assembly: both sides assemble through the same
     `DriverReport` checked transitions
     (`crates/kryprobe-core/src/backend/driver.rs:240`):
     `extend_observations`, `push_summary`, exactly-once
     `feed_shared_losses` (`:269`), and
     `session_integrity_checked` (`:354`) — live at
     `live.rs:1724-1733` (aggregate) and `live.rs:2086-2100`
     (lifecycle, where the feed is zero because drain losses
     already ride the summary).
   - Observation/coverage vocabulary: `NativeObservation`
     (`crates/kryprobe-core/src/evidence/observation.rs:119`),
     `CoverageSummary`
     (`crates/kryprobe-core/src/evidence/coverage.rs:133`),
     `DimensionCoverage` (`:25`), `IntegritySummary`,
     `SharedLosses`, and the all-`NotRun` baseline
     (`CoverageSummary::not_run`, `:157`) shared by the batch
     harness (`BackendDriver::harness`,
     `driver.rs:101`) and the live finalize contexts.
3. Each side owns what the other cannot reproduce, and the
   conformance suite must not compare across the ownership line:
   - Batch owns: pre-run routing validation
     (`DriverError::UnroutedEvent`, `driver.rs:129-133`),
     registration-order × input-order observation sequence
     (`driver.rs:191-203`, every decode appended), capability
     skip receipts (`SkippedBackend`, `driver.rs:224`).
   - Aggregate-live owns: the snapshot tick loop
     (`drive_session_inner`, `live.rs:1525`), the
     `SessionSensor` seam (`live.rs:1210`, production
     `RealSensor` at `:1233`, scripted `ScriptedSensor` in
     `crates/kryprobe-cli/tests/live_session.rs:999`),
     latest-per-key upsert (`live.rs:1609` and neighbors —
     repeats collapse, ids go sparse, never renumbered), who
     attribution via `observation_for_who`
     (`crates/kryprobe-privilege/src/kcrypto_backend/observe.rs:338`,
     ids minted directly from the session issuer at
     `live.rs:1658-1660`), and `session_coverage` (`live.rs:739`).
   - Lifecycle-live owns: the sustained ring drain + readiness
     wait (`drive_lifecycle_session_inner`, `live.rs:1875`), the
     `LifecycleSessionSensor` seam (`live.rs:1295`, production
     `RealLifecycleSensor` at `:1349`, scripted
     `ScriptedLifecycleSensor` in
     `crates/kryprobe-cli/tests/live_session.rs:1911` and
     `ScriptedOutputSensor` in
     `crates/kryprobe-cli/tests/kcrypto_output.rs:565`),
     stop-time `finish` reconciliation, the 100K observation cap
     with counted omissions (`live.rs:1920-1924`), and
     `lifecycle_coverage` (`live.rs:866`).
   - Both live sides own the ARCH §4.1 governed tail
     (`SessionController` hops to `Finalized` at
     `live.rs:1750`/`live.rs:2117`; failure parks in
     `FailedPartial` at `:1504`/`:1856` in the drive
     wrappers, `:2214`/`:2371` in the bring-up wrappers)
     and bring-up order
     (gate → detect → plan → configure in
     `run_live_session_inner`, `live.rs:2376`, and
     `run_lifecycle_session_inner`, `live.rs:2219`); the batch
     driver has no sensor, no clock, and no session machine.
4. Seam contract — same stream in, equal observations + coverage
   out, modulo the normalizations below. Each invariant names the
   exact types compared:
   - I1 (observations): `Vec<NativeObservation>` from the batch
     `DriverReport::observations` vs the live
     `LiveOutcome.observations`, compared as multisets with
     `id: ObservationId` stripped (batch issues in
     registration × input order from its own `IdIssuer`;
     aggregate-live issues in tick/row order with who ids
     interleaved and evicted-tick gaps; lifecycle-live issues
     in completion order — issuance order is driver-owned).
     All other fields compare exact, INCLUDING
     `started_ns`/`ended_ns`: decode stamps them from row
     payload (`observe.rs:217-218` agg/totals,
     `:286` ident, `:388-389` who; lifecycle `None` at
     `kcrypto_lifecycle/backend.rs:577-578`), never from a
     driver clock. Multiset — not sequence — comparison because
     issuance order is driver-owned (above), NOT to reconcile
     latest-per-key collapse: aggregate-live upserts while batch
     appends, which changes counts, so duplicate-key streams are
     excluded by scripting (fixtures use distinct keys only).
   - I2 (coverage): `CoverageSummary` per-dimension `status:
     CoverageStatus` plus `counters: Vec<DimensionCounter>`
     compare exact; `interval: ValidityInterval` walls are
     normalized away (start shifted to 0 / end to duration, or
     dropped). Live walls are measured `CLOCK_MONOTONIC`
     (`live.rs:1567-1572` snapshots, `live.rs:1950-1952` ring
     clock); the batch driver has no clock — coverage there is
     input session state (`BackendDriver::new`, `driver.rs:67`),
     so the conformance harness supplies the expected summary
     for the scripted stream and normalizes walls before
     comparing.
   - I3 (integrity): `IntegritySummary` from
     `DriverReport::session_integrity_checked` on both sides
     compares exact, no normalization (counts only). Both
     sides must feed (`feed_shared_losses`) before comparing —
     aggregate-live from measured drop counters
     (`live.rs:1728-1730`), lifecycle-live the required zero
     (`live.rs:2095-2097`); an unfed side refuses instead of
     comparing.
   - I4 (per-backend facts): `Vec<BackendSummary>`
     (`backend`, `observations`, `integrity`) compares exact
     per backend, plus `Vec<SkippedBackend>` receipts exact
     under identical `RuntimeCapabilities` (same gates ⇒ same
     skips; skip-drop counts are driver-observed, not
     clock-derived).
   - I5 (decoder identity): both sides must resolve the same
     `Backend::decode` implementation through the same
     `BackendRegistry` + `register_kcrypto_profile` selection —
     conformance never compares observations across different
     decoders. Profile dispatch is pinned at
     `live.rs:2160-2175`; registry order pins batch sequence.
5. Drift between the drivers is gated by the Task 2 conformance
   suite, which implements I1–I5 over scripted streams through
   the existing scripted sensors (`ScriptedSensor`,
   `ScriptedLifecycleSensor`, `ScriptedOutputSensor`) and the
   batch `BackendDriver::harness`. Convergence of the two
   drivers remains possible later but is explicitly not required
   by this decision.

## Consequences

- Task 2 builds the conformance suite against invariants I1–I5;
   any driver change that breaks an invariant fails the suite
   and must either fix the driver or amend this ADR.
- New backends and profiles inherit the contract automatically:
   they implement the frozen `Backend` trait (shared decode +
   finalize), so both drivers pick them up through the registry
   with no per-driver wiring.
- The P2 convergence item from `krypto-audit-fixes` is closed as
   "blessed, will not converge": future audit rounds cite this
   ADR instead of re-raising the split.
- No code, test, or CI change ships with this ADR; follow-up
   tasks reference it by number.

# ADR-0004: Kernel-crypto-only product scope

## Status

Accepted (owner-directed 2026-09-24).

## Context

KryProbe shipped a thin-spine skeleton with four backend rows
(`synthetic`, `p11`, `openssl`, `kcrypto`) and an `import` command
that ingested osslscope/p11scope docs as shell JSONL. Only the
kcrypto backend ever observed anything live; the p11/openssl rows
were static `not installed` states and `import` was the sole active
third-party surface.

Carrying PKCS#11 provider discovery, function-table variants, and
process-lifecycle complexity as KryProbe's own scope was rejected:
p11scope's complexity should not become KryProbe's complexity.

## Decision

KryProbe's product is a Linux Kernel Crypto API runtime observer:

- No `import` command: any `import` argv is an unknown subcommand
  (usage error, exit 2) and reads no input.
- No active p11/OpenSSL backend rows: `backends`/`doctor` list
  `synthetic` (test-only) and `kcrypto` (live-gated) only.
- New capture sessions select only `kernel-crypto` (`--source`
  rejects anything else at parse, and the live session refuses
  anything else at admit).
- OpenSSL observation is an optional future decision, not a
  requirement; PKCS#11/p11scope is out of scope entirely.

## Compatibility

Already-issued wire identifiers are frozen and never reassigned:
`p11=1` is retired/reserved, `openssl=2` reserved for possible
future use, `kcrypto=3`, `synthetic=255` (test-only). The
`BackendId::P11`/`OpenSsl` enum cases remain as compatibility-only
decoders for legacy data and generic tests.

Old schemas stay byte-identical (`schemas/event-v0.schema.json`,
`schemas/shell-v1.schema.json`). Historical `import_shell` records
(`kryprobe/shell/v1`) still validate structurally via `report
FILE`; nothing produces new ones. An inert legacy decoding case or
schema record is not an active integration commitment.

## Consequences

Positive:

- One honest observation boundary: kernel crypto selection and
  workload at explicitly described coverage.
- No userspace-provider scope debt in the CLI, report, or loader
  surfaces.

Negative:

- Third-party docs have no ingestion path; historical shells are
  read-only evidence.
- Any future OpenSSL work needs its own ADR and must not assume
  the retired `import` shape.
